# הפיכת הריפו לפרטי — ושהשרת ימשיך למשוך עדכונים

המסמך הזה עונה על שאלה אחת: **הפכתי את הריפו ב-GitHub לפרטי. איך השרת ימשיך למשוך עדכונים?**

## אין שם משתמש ואין סיסמה

זו הנקודה שמבלבלת, ולכן היא ראשונה: **בשיטה שכאן אין שם משתמש ואין סיסמה.**
במקומם יש **מפתח** — קובץ שנוצר על השרת פעם אחת. החצי הציבורי שלו מודבק ב-GitHub,
החצי הפרטי נשאר על השרת ולא זז משם. GitHub מזהה את השרת לפי המפתח, בדיוק כמו
שמנעול מזהה מפתח — בלי שאף אחד מקליד דבר.

לכן, אם אתם מחפשים בפלט של הפקודות "שם משתמש" או "סיסמה" — אין. הדבר היחיד
שתעתיקו הוא תוכן קובץ אחד (`.pub`), וזה מה שמודבק ב-GitHub.

הערך היחיד שתצטרכו למלא בעצמכם הוא **שם המשתמש של לינוקס על השרת** — כלומר
המשתמש שאתם מחוברים בו ב-SSH. הפקודה `whoami` מדפיסה אותו, ו-`echo $HOME` מדפיסה
את תיקיית הבית שלו (למשל `/home/ubuntu` או `/root`). זה לא סיסמה, וזה לא סוד.

## למה מפתח פריסה (Deploy Key) ולא טוקן

| | Deploy Key (מומלץ) | טוקן אישי (PAT) בכתובת ה-remote |
|---|---|---|
| היכן נשמר | קובץ ב-`~/.ssh`, הרשאות 600 | טקסט גלוי בתוך `.git/config` |
| תוקף | לא פג | פג בשקט, והעדכונים נעצרים בלי הודעה |
| היקף | ריפו אחד בלבד | כל הריפואים של המשתמש |
| כתיבה | אפשר לאסור לגמרי (קריאה בלבד) | בדרך כלל גם דחיפה |
| ביטול | מחיקה אחת ב-GitHub | ביטול הטוקן פוגע בכל מקום שבו הוא בשימוש |

השרת רק **מושך** קוד — הוא לעולם לא דוחף. לכן מפתח לקריאה בלבד הוא בדיוק מה שנדרש,
ולא יותר. אם המפתח דולף, מי שמחזיק בו יכול לקרוא את הקוד ולא לשנות אותו.

**אין להטמיע טוקן בתוך כתובת ה-remote.** כתובת כזו נשמרת ב-`.git/config` בטקסט
גלוי, מודפסת בכל `git remote -v`, ומגיעה ללוגים של סקריפטים. סוד ששוכב בקובץ
תצורה אינו סוד.

## הסדר חשוב: קודם המפתח, אחר כך פרטי

עשו את כל השלבים כאן **לפני** שאתם הופכים את הריפו לפרטי. ריפו ציבורי נמשך בלי
הזדהות, ולכן אפשר לבדוק שהכול עובד בזמן שהרשת פתוחה. אם תהפכו לפרטי קודם, העדכון
הבא ייכשל ותצטרכו לתקן תחת לחץ.

## מי המשתמש שצריך את המפתח

העדכונים רצים משורת cron (`docker/deploy-watcher.sh`), והיא רצה תחת משתמש מסוים.
המפתח חייב להיות של **אותו** משתמש — מפתח שיושב אצל משתמש אחר פשוט לא ייקרא.

```bash
whoami        # המשתמש שאתם מחוברים בו עכשיו
crontab -l    # אם רואים כאן את deploy-watcher — זה המשתמש הנכון
```

אם השורה אינה מופיעה, בדקו גם `sudo crontab -l` (cron של root) ו-`sudo crontab -l -u www-data`.
אם ה-cron רץ תחת root — הריצו את כל הפקודות שלהלן תחת root.

## השלבים

### 1. יצירת המפתח על השרת

```bash
ssh-keygen -t ed25519 -f ~/.ssh/multioto_deploy -N "" -C "multioto server"
```

נוצרים שני קבצים: `~/.ssh/multioto_deploy` (הפרטי — נשאר על השרת) ו-`~/.ssh/multioto_deploy.pub`
(הציבורי — מיועד להדבקה ב-GitHub).

### 2. רישום GitHub כמארח מוכר

```bash
ssh-keyscan github.com >> ~/.ssh/known_hosts
```

בלי זה, החיבור הראשון עוצר בשאלה `Are you sure you want to continue connecting?`,
ו-cron אינו יכול לענות עליה — העדכון פשוט ייתקע.

### 3. הדבקת המפתח הציבורי ב-GitHub

```bash
cat ~/.ssh/multioto_deploy.pub
```

הפלט הוא שורה אחת שמתחילה ב-`ssh-ed25519`. העתיקו אותה **במלואה** אל:

**GitHub → הריפו `multidigitalltd/multioto` → Settings → Deploy keys → Add deploy key**

* Title: `multioto server` (שם לזיהוי בלבד)
* Key: השורה שהעתקתם
* **Allow write access — להשאיר לא מסומן.** השרת רק מושך.

### 4. הפניית הריפו על השרת ל-SSH

```bash
cd /path/to/multioto          # התיקייה שבה יושב הפרויקט על השרת
git remote set-url origin git@github.com:multidigitalltd/multioto.git
git config core.sshCommand "ssh -i $HOME/.ssh/multioto_deploy -o IdentitiesOnly=yes"
```

`$HOME` מתרחב לבד לתיקיית הבית של המשתמש הנוכחי — אין צורך למלא שם ידנית.
אם אתם מריצים את השורה הזו תחת משתמש אחד ואת ה-cron תחת אחר, כתבו את הנתיב
המלא במקום `$HOME` (למשל `/home/ubuntu/.ssh/multioto_deploy`).

`IdentitiesOnly=yes` אומר ל-SSH להשתמש במפתח הזה בלבד. בלי זה, אם יש על השרת
מפתחות נוספים, SSH ינסה אותם לפי הסדר, GitHub ידחה אותם, והחיבור עלול להיכשל
עוד לפני שהמפתח הנכון הגיע לתור.

### 5. בדיקה — עכשיו, בזמן שהריפו עדיין ציבורי

```bash
ssh -T -i ~/.ssh/multioto_deploy -o IdentitiesOnly=yes git@github.com
```

תשובה תקינה: `Hi multidigitalltd/multioto! You've successfully authenticated, but GitHub does not provide shell access.`
המילים `does not provide shell access` הן חלק מהתשובה התקינה — לא שגיאה.

ואז:

```bash
git fetch origin && echo "עובד"
```

### 6. עכשיו אפשר להפוך את הריפו לפרטי

**GitHub → Settings → General → Danger Zone → Change repository visibility → Private.**

מיד אחר כך, ודאו שוב:

```bash
./update.sh
```

## אם משהו נשבר

| מה רואים | מה זה אומר |
|---|---|
| `Repository not found` | המפתח לא הודבק, הודבק בריפו אחר, או ה-remote עדיין `https://` |
| `Permission denied (publickey)` | ה-`core.sshCommand` לא הוגדר בתיקייה הזו, או שהוא מצביע על נתיב שגוי |
| `Host key verification failed` | דילגתם על שלב 2 (`ssh-keyscan`) |
| עובד ידנית ולא ב-cron | המפתח שייך למשתמש אחר מזה שמריץ את ה-cron — ראו למעלה |
| בקשה לשם משתמש וסיסמה | ה-remote עדיין `https://`. חזרו לשלב 4 |

בכל מקרה של תקלה, הפקודה שמראה את המצב האמיתי היא:

```bash
git remote -v && git config core.sshCommand
```

## ביטול גישה

מחיקת המפתח ב-GitHub (Settings → Deploy keys → Delete) חוסמת את השרת מיד. אין
צורך לגעת בשרת, ואין השפעה על שום ריפו אחר. זה גם מה שעושים כששרת מוחלף או מושבת.

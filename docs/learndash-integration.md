# LearnDash integration: API evidence and acceptance

This document records the native API evidence and acceptance requirements for the site-agent LearnDash adapter. Availability is determined on the connected WordPress site; a function name appearing below is not a guarantee that every LearnDash version provides it.

## Scope

The adapter's bounded scope is course discovery, course-context content reads, learner progress, groups, direct course enrollment and group membership. Mutations use the existing proposal, approval, stale-state check and undo flow. Native snapshots stay in sealed server-side state, outside the conversation model's arguments.

Course titles and body content can use the existing content-editing flow. Generic WordPress content support alone does not create a working LearnDash quiz, attach a lesson to a course or maintain shared course steps. New course/lesson/topic text may be saved as an unassigned draft only when the available content tool supports it; this must not be described as a completed course structure.

The following are outside this adapter's write scope:

- Course-builder relationships and group-to-course assignments. A public example of adding a course to a group was found, but the complete reversible write contract was not verified.
- Quiz questions, attempts, grades, certificates and progress/completion changes or resets.
- Course pricing, checkout, subscription/access-rule configuration and bulk enrollment.
- Legacy direct enrollment and any enrollment state the adapter cannot read and restore exactly.

Student-specific membership/progress reads and writes are unavailable on WordPress multisite until LearnDash's native metadata namespace is verified. The observed raw usermeta keys contain post IDs but no blog identifier; checking current-blog membership alone cannot rule out collisions for users enrolled on two blogs. Current-blog course/group catalog and hierarchy reads remain in scope; group-member details do not.

Direct course writes on supported single-site installations additionally require at most 1,000 users in the WordPress user store and the native expired-enrollment lookup described below. Larger installations retain the supported reads; the direct write is unavailable because the verified expiry-marker API returns a course-wide list. Courses with access expiration enabled are not writable through this adapter. Group membership is separately conditional on the affected course policies and access being understood.

Direct enrollment and effective access are separate facts. Removing a direct enrollment may leave access through a group or an open course. The adapter must report the change it actually made and must not remove group membership implicitly to force access revocation.

The native read tools are `ld_capabilities`, `ld_courses_list`, `ld_course_get(course_id)`, `ld_student_course_get(user_id, course_id)`, `ld_groups_list` and `ld_group_get(group_id)`. Membership uses the selector `{user_id, kind: "course" | "group", target_id}` with `ld_membership_get`, `ld_membership_prepare`, `ld_membership_apply` and `ld_membership_revert`.

A membership read reports the user/target identity, `direct_member`, `effective_access`, `access_sources`, `access_from`, `expires_at`, and whether the selector is writable with an explanatory reason. Preparation returns the before/after state, affected course-access information and sealed approval state. A missing API or unsupported policy must remain visible as an unavailable capability; it must not silently become an empty enrollment list.

Catalog/member pages use `page` and `limit`, with at most 100 records per page; catalog search uses `search`. Hierarchy and membership-context reads reject lists or combined group-to-course relationships exceeding the adapter's 200-item bound rather than silently hiding affected courses. Group-member pages read the verified membership metadata through bounded WordPress user queries and omit privileged users.

## Modern direct-enrollment guard

1. Refuse student-specific reads and mutations on multisite before inspecting global enrollment metadata. On a supported installation, confirm the target user and `sfwd-courses` post exist and the sender has the required permission. Require the native read/write functions needed for the requested operation.
2. Require an available `learndash_use_legacy_course_access_list()` returning `false` for direct writes. Otherwise keep direct enrollment read-only and explain the missing capability.
3. Read only the selected user's `course_<course_id>_access_from` metadata with WordPress metadata APIs. Keep an explicit existence flag and exact stored value. Reject multiple rows or malformed values rather than normalizing them into a new agreement.
4. Keep inherited/group access separate. An effective-access boolean is neither a direct-enrollment identifier nor an undo snapshot. Check the course-level expiry policy before creating enrollment: a previously unenrolled user's zero expiry does not establish that the course has no expiration policy. Also check old native expired-enrollment state using the bounded lookup above, even if the course currently has expiration disabled. Expiring or otherwise unsupported native state must remain read-only until its restoration contract is established. Include the policy in the conflict fingerprint.
5. Prepare a sealed snapshot without writing. Apply only after approval, a fresh comparison and the adapter's mutation lock. Use the native enrollment API, then read back the supported state; do not assume that a truthy return value proves success.
6. Undo only when the supported state still matches the successful apply snapshot. Use the native inverse operation, then restore the original access-date existence/value through WordPress metadata APIs and verify it. Calling enroll again and keeping its new timestamp is not an exact undo.
7. Never call progress, attempt or grade deletion/reset functions as part of enrollment or its undo. Interoperating enrollment callers inspected here do not add a progress-reset step. This does not prove that arbitrary third-party hooks on a live site have no side effects.

The same proposal/approval/conflict rules apply to group membership. A group membership change must not assign the `group_leader` WordPress role, change group administrators, or perform a second hidden course-enrollment mutation.

The adapter also reads only the selected user's `learndash_group_users_` metadata rows through a prepared, prefix-restricted query capped at 201 rows. It accepts at most 200 unique canonical group keys with matching numeric values and compares them with LearnDash's group reader. These rows become part of the sealed conflict snapshot. A stale or inconsistent inverse group cache therefore makes the membership read-only and prevents applying an outdated access prediction. This query does not load unrelated user metadata.

If the native vendor call changes state and then throws before the adapter can verify its result, the adapter reports that manual inspection is required. It does not claim successful rollback or overwrite an unverified concurrent change. The same applies if the mutation lease expires or is replaced; subsequent writes and compensation stop. Notifications and external integration side effects are outside the supported state rollback.

## Generic-tool boundaries

LearnDash relationships and state must not be writable through the generic custom-field fallback. On LearnDash objects, protect native relationship keys such as `course_id`, `lesson_id` and `quiz_id`, the `sfwd-` / `_sfwd` key families, and LearnDash internal metadata prefixes. An ACF field mapped to a protected native key must not bypass that boundary.

`post_parent` and `menu_order` are not a replacement for LearnDash's course builder. Internal LMS records, including student attempts and graded submissions, must not be treated as ordinary draft/publish/trash content merely because they expose an admin screen.

## Validation status and test-site acceptance

No licensed live LearnDash installation was available in this development environment. Requests to the official LearnDash developer documentation were blocked by the environment's outbound proxy with HTTP 403. The source review above supports interoperability decisions; fixture tests do not establish compatibility with every released version or customer extension.

Before enabling this integration on a customer site, use a test site with the intended LearnDash version and record its version, course configuration and active enrollment-related integrations. Complete the following checks with test users:

- Verify inactive/missing LearnDash and missing individual functions produce an unavailable/read-only capability rather than a fabricated empty result or a PHP error.
- Read courses, lessons, topics, quizzes and a shared step attached to two courses. Confirm each relationship is reported in the requested course context. Check size limits and pagination on large datasets.
- Read not-started, partially completed, completed and zero-step courses. Compare the result with LearnDash's administration UI without changing progress or attempts.
- Grant direct enrollment to a user with no direct enrollment, verify native access, retry the same request and undo it. Confirm the original absence of enrollment metadata is restored.
- Remove and undo an existing supported direct enrollment with an old access timestamp. Confirm the original timestamp and expiry are unchanged, not restarted from the undo time.
- Check existing expired/future-expiring enrollment, an unenrolled user on an expiring course, legacy enrollment mode, malformed/multiple native metadata rows and any missing restoration dependency. Unsupported writes must be refused before they change state. A normal non-expiring course must still allow a new enrollment.
- Check a user with a native expired marker after course expiration has been disabled. Direct enrollment must still be refused. Check the 1,000/1,001-user boundary and unknown user counts; the large/unknown case must not invoke the course-wide expired-user lookup or perform a direct write.
- Check a user with group-only access, and a user with both direct and group access. Removing direct enrollment must not remove group membership or claim that all course access ended.
- Add/remove group membership and undo both changes. Verify group leaders, other group memberships, course progress and quiz attempts remain unchanged.
- Change the relevant enrollment state in WordPress between prepare/apply and between apply/undo. Verify conflict rejection preserves the intervening change. Check replay, tampered receipts and another site's/user's identifiers.
- On multisite, verify membership/progress reads and all membership mutations are unavailable for both single-blog and dual-blog users, including colliding post IDs. Group catalogs must not expose member details; current-blog catalog/hierarchy reads should continue to work.
- Attempt the same native relationship change through generic fields, ACF and content scheduling/parent tools. Protected LMS state must remain inaccessible through those routes.
- Observe emails, webhooks, CRM sync and payment/membership extensions triggered by enrollment on the test site. Undo restores supported state; it cannot retract a notification or reverse an independent external action.

Do not describe this acceptance as completed until the live checks have actually been run and their results recorded.
